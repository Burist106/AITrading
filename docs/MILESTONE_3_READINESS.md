## Transaction-time documentary evidence (2026-09-21)

This is a documentation-only research update. No native diagnostic or full smoke was rerun for it; earlier verification results above retain their original scope.

| Question                                        | Explicit primary-source evidence                                                                                                                                                                                                                                                                                                                                                          | Remaining limitation                                                                                                                                                                                                         |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What do the Python history functions represent? | [MQL5 AlgoBook: Python order/deal history](https://www.mql5.com/en/book/advanced/python/python_history_deals) maps returned fields to native Order/Deal properties and describes the functions as equivalents or analogs of native history operations. Date arguments accept datetime objects or seconds since 1970.                                                                      | Functional equivalence does not explicitly specify aware-Python-datetime serialization or the timezone interpretation of every returned numeric field. Examples without independent timezone annotations cannot settle this. |
| Which time selects native historical records?   | [MQL5 AlgoBook: history selection](https://www.mql5.com/en/book/automation/experts/experts_history_select) specifies server-time bounds, both endpoints inclusive, and selects historical Orders by `ORDER_TIME_DONE`, not setup time. Successful empty selections are possible.                                                                                                          | These are explicit native-MQL5 semantics. Applying them across the Python bridge, including subsecond boundary behavior, still needs evidence.                                                                               |
| What are transaction time fields?               | The official [Order](https://www.mql5.com/en/docs/constants/tradingconstants/orderproperties), [Position](https://www.mql5.com/en/docs/constants/tradingconstants/positionproperties), and [Deal](https://www.mql5.com/en/docs/constants/tradingconstants/dealproperties) property tables identify event fields, datetime types, and corresponding millisecond values measured from 1970. | Units and field identity alone do not establish whether the Python number encodes UTC event time or a server-wall-clock label.                                                                                               |
| What is the provider clock?                     | [Pepperstone trading hours](https://pepperstone.com/en-gb/about-us/trading-hours) describes GMT+3 during US daylight saving and GMT+2 otherwise.                                                                                                                                                                                                                                          | A provider clock rule does not specify Python transaction serialization. The validated market-only mapping must not be generalized to transactions.                                                                          |

Inference, not an established runtime rule: the functional correspondence makes native server-time selection a useful hypothesis for a future bridge validation. It does not justify subtracting three hours from all transaction fields, changing the UTC default, or treating the existing inventory envelope as a validated query interval.

The missing proof is a field-specific Python bridge contract for the consumed Position/Order/Deal times, plus exact history-bound serialization and selection behavior. Alternatively, an existing independently timed sample set could test those claims without manufacturing trades. No such sample set is currently available. Future validation must distinguish setup from completion, seconds from milliseconds, zero/sentinel fields, and endpoint inclusion; a fake-backed test can verify an implementation but cannot establish the broker contract. Public forum suggestions are not vendor confirmation.

Until that evidence exists, retain real-source `NOT READY`, the transaction read gate, and the blocked full-smoke result. The later explicit Milestone 3 implementation authorization does not weaken these acceptance criteria, authorize a support request, or publish this patch.
