## Fixed assumptions

- The root of the extracted `Aurum_Codex_Starter_Pack` folder is the project root.
- All market/account/order values are fictional design fixtures.
- No real Supabase project, MT5 terminal, LINE channel, or API account is required for installation or tests.
- Local Supabase is optional in Bootstrap because the migration contains no executable schema.
- The `0.01` volume is a maximum. The minimum-lot scenario deliberately has calculated volume 0.0045 and no requested volume.
- A future Worker execution port may describe a boundary but must remain without a broker implementation until explicitly authorized.

## Known Bootstrap limitations

- Static health states do not prove any external system is healthy.
- Contract compatibility is tested only for representative Bootstrap messages, not a live control plane.
- Emergency acknowledgement, approvals, pending/rejected orders, and positions are fixture states.
- No operational RLS, authentication, persistence, reconciliation, or recovery exists yet.
- The exact next authorized task is **Milestone 1 — Supabase Domain and Security Foundation**.

## Milestone 1 assumptions and unresolved operational decisions

- The deterministic local Auth owner is fictional, has an `.invalid` email address, and has no seeded password. Tests authenticate by local JWT claims rather than real login information.
- The dedicated Worker authorization tests use fake local claims containing `role=aurum_worker`, `owner_id`, and `worker_id`. Hosted claim issuance, rotation, and revocation are an operational decision for a later deployment task; Milestone 1 creates no remote credential.
- `notifications`, mobile approval sessions, user notes, candles, strategy runs, journals, analytics, and model tables are omitted because no existing Milestone 1 contract requires them. Adding them would start deferred P0/P1 behavior speculatively.
- Numeric database values are authoritative for money, price, percentage, and volume. Generated TypeScript values require deliberate adapters before arithmetic. Milestone 1 Python wire models validate finite numeric inputs but perform no financial arithmetic; a later arithmetic milestone must adopt and test an explicit decimal-conversion policy before calculations.
- Security-relevant successful actions and deterministic domain rejections can be audited in their transaction. A PostgreSQL permission denial rolls back its transaction, so failed authorization attempts belong in platform/authentication logs rather than an impossible same-transaction audit insert.
- Existing 20 development scenarios remain presentation-only fixtures. Executed, order, Position, and Emergency Stop visuals are not inserted as operational seed records and do not represent a functioning execution path.
- Proposal read models expose proposal facts and normalized risk checks separately. They do not infer executable eligibility, and missing or expired heartbeat data maps to `unknown` rather than a healthy state.
- At the Milestone 1 audit, the project root contained local `.git` metadata, but its branch had no commits and no remote. Milestone 1 therefore preserves the deliverable as reviewable working-tree changes and does not fabricate a baseline commit, tag, or push destination.
- After Milestone 1 completion, the user explicitly authorized publication to `Burist106/AITrading`. The existing remote `README.md` commit is preserved, the project is added on top of `main` without force-push, and GitHub Actions verified both clean-checkout jobs on implementation commit `ab7df47`.
- Local queue tests may create fictional Worker claims and operational rows inside rolled-back test transactions. They are evidence for database behavior only and do not represent a deployed Worker, broker session, order, execution, or Position mutation.
- The two-session queue test assumes local peer access and the existing `postgres` to `aurum_worker` SET capability inside the pinned Supabase database container. It never reads or requests a database password and never changes role membership; cleanup verifies the baseline capability remains present, while any failed path destroys the isolated database volume.
- The current deployment model is explicitly one owner, one Demo account binding, and one active risk policy. Multiple accounts, broker sessions, or active policy selection are unresolved future architecture and are not inferred by Milestone 2.

## Milestone 2 assumptions and unresolved limitations

- The deployment remains single-owner, single-Demo-account binding, single confirmed broker symbol, and single Worker process. Multi-account selection and distributed native ownership are not designed.
- The local Terminal installation, Demo session, Market Watch visibility, and broker-specific XAUUSD symbol are operator prerequisites. The Worker does not install a Terminal, enable a symbol, or sign in.
- Latest tick persistence is intentionally bounded to one versioned current row per owner/account/symbol. Candle and raw tick history persistence are deferred.
- The P0 browser adapter derives a safe health projection from available observation rows; terminal version and last completed candle remain nullable when no persisted source exists.
- The browser uses the bounded latest-tick upsert as its Milestone 2 liveness signal because routine tick polling intentionally does not append audit rows or persist an unbounded heartbeat stream. This is a read-model assumption, not proof of a live broker session.
- Hosted Worker claim issuance, secret rotation, deployment, monitoring, and remote Supabase configuration remain unresolved and were not performed.
- Changed-specification confirmation remains an operationally manual or future-authorized setup operation. This patch intentionally exposes no browser or Worker confirmation action.
- The source-review patch assumes one bounded 24-hour history request can prove only that exact request completed; it makes no claim about unlimited broker retention outside the requested window.
- The real-terminal smoke is `NOT RUN` because no explicitly opted-in eligible local Demo Terminal configuration was supplied. Deterministic tests and Windows import checks are not a substitute for that smoke.
- Milestone 3 strategy, eligibility, Risk Engine, proposal production, command consumption, and every execution capability remain unstarted.
